# MIREA-RAG на GPU вуза

Сервис работает на инфраструктуре РТУ МИРЭА. Ниже приведена воспроизводимая конфигурация для нового развёртывания. GPU-сервер запускает vLLM с Qwen3-8B-AWQ. В примере бот, Ollama с BGE-M3 на CPU и Qdrant работают на другой Linux-VM. Прокси вуза предоставляет боту внутренний HTTPS-адрес сервиса vLLM. Если на сервере запускаются задания через Slurm, поднимайте vLLM внутри выделенного задания. Для постоянной работы нужен ресурс, который остаётся выделенным на время работы бота.

## GPU-сервер

Уточните у администратора, как передаётся доступ к выделенным 20 ГБ. Для MIG на Docker обычно используется назначенный UUID из `nvidia-smi -L`. Если планировщик уже ограничивает видимые устройства, используйте окружение, выданное планировщиком, и команду `vllm serve` с теми же параметрами модели. Не указывайте индекс всей H100 вместо назначенного устройства.

Пример для NVIDIA Container Toolkit и HTTPS-прокси на том же GPU-сервере. Контейнер публикует порт только на loopback. VM приложения обращается к прокси по адресу `LLM_BASE_URL`; настройка прокси и выдача сертификата выполняются на стороне инфраструктуры вуза. Укажите `MIG_UUID` и передайте `VLLM_API_KEY` из хранилища секретов в окружение процесса запуска. Первый запуск загружает веса с Hugging Face. Если исходящий доступ закрыт, используйте заранее скачанные веса, смонтированные в контейнер, и укажите локальный путь модели. В примерах используются теги `latest` для vLLM и Ollama. При обновлении зафиксируйте проверенные версии или digest образов и ревизию весов, чтобы можно было восстановить прежнюю конфигурацию.

```bash
: "${MIG_UUID:?Укажите UUID выделенного MIG-устройства}"
: "${VLLM_API_KEY:?Задайте ключ для vLLM}"
docker run -d --name mirea-vllm --restart unless-stopped \
  --gpus "device=${MIG_UUID}" --shm-size=2g \
  --publish 127.0.0.1:8000:8000 \
  --mount source=mirea-models,target=/root/.cache/huggingface \
  --env VLLM_API_KEY --env VLLM_NO_USAGE_STATS=1 \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen3-8B-AWQ \
  --served-model-name mirea-qwen \
  --max-model-len 12288 --gpu-memory-utilization 0.85 --max-num-seqs 4 \
  --enable-auto-tool-choice --tool-call-parser hermes
```

Проверьте `docker logs -f mirea-vllm` и затем `GET /v1/models` с заголовком `Authorization: Bearer …` с машины бота через внутренний прокси. Прокси должен пропускать заголовок авторизации, а его таймаут должен позволять завершать запросы модели из тестового прогона. 12 288 токенов и 4 последовательности — стартовые параметры. При нехватке памяти уменьшите контекст или параллелизм, затем проверьте, что исходный промпт реранкера и агента помещается вместе с ответом. Лимит ответа приложения — 1024 токена на вызов.

## Машина приложения

Перед первым запуском создайте `.env.campus` из примера. `LLM_BASE_URL` — внутренний HTTPS-адрес с суффиксом `/v1`, `LLM_API_KEY` — тот же ключ, что задан vLLM. Для пилота используйте отдельный токен Telegram. Если переносите действующего бота, остановите предыдущий экземпляр перед переключением токена.

```bash
cp .env.campus.example .env.campus
chmod 600 .env.campus
# Заполните .env.campus перед следующими командами.
dc() { docker compose -p mirea-campus -f compose.campus.yml "$@"; }

dc up -d qdrant embeddings
dc build bot

# Из сети Compose проверьте готовность Qdrant и доступность Ollama.
dc run --rm --no-deps -T bot python - <<'PYTHON'
from time import sleep
from urllib.error import URLError
from urllib.request import urlopen

for url in ("http://qdrant:6333/readyz", "http://embeddings:11434/api/tags"):
    for attempt in range(30):
        try:
            with urlopen(url, timeout=2):
                print(f"Готов: {url}")
            break
        except (URLError, TimeoutError):
            if attempt == 29:
                raise
            sleep(1)
PYTHON
```

После того как обе проверки вернули «Готов», выполните следующие команды.

```bash
dc exec embeddings ollama pull bge-m3
dc run --rm --no-deps bot python -m rag.index --reembed-from index/api/chunks.json
dc run --rm --no-deps bot python -m rag.qdrant_store
dc run --rm --no-deps bot python -m rag.check_campus
dc up -d bot
dc logs -f bot
```

`dc up -d` запускает контейнеры. Готовность зависит от ответа внутренних HTTP-проверок. Если проверка завершилась ошибкой, посмотрите `dc logs qdrant embeddings` и повторите её перед индексацией.

## Обновление индекса

`--reembed-from index/api/chunks.json` берёт фрагменты из текущей копии репозитория и заново считает их локальной BGE-M3. Таблица программ читается отдельно из `index/programs.json`, который включается в образ при сборке. При переходе на новую приёмную кампанию обновите фрагменты и таблицу программ, затем пересоберите образ бота и индекс. При смене модели эмбеддингов пересчитайте векторы всех фрагментов. Обычный перезапуск бота использует уже заполненную коллекцию.

Команда `rag.qdrant_store` пересоздаёт коллекцию `mirea`. Для обновления сначала остановите бота, сохраните резервную копию текущей коллекции или держите под рукой её проверенный индекс, затем загрузите новую версию и запустите `rag.check_campus`. После успешной проверки запустите бота снова, чтобы он заново загрузил фрагменты для BM25. Для проверки без остановки рабочего экземпляра используйте отдельный Compose-проект со своими томами и тестовым токеном бота.

## Проверка и диагностика

- **GPU и прокси.** Начните с авторизованного запроса к `/v1/models` с VM бота. Проверьте, что в ответе есть имя `mirea-qwen`. `401` указывает на проблему с авторизацией. `502/504` требуют сверить доступность vLLM и таймаут прокси. Если прокси использует внутренний центр сертификации, доверенный корневой сертификат должен быть доступен клиенту внутри контейнера бота.
- **Сквозная проверка.** `rag.check_campus` делает генерацию, получает эмбеддинг, читает Qdrant и проверяет два сценария агента. После запуска отправьте тестовый вопрос через Telegram, чтобы дополнительно проверить polling, токен и доставку сообщения.
- **Задержка и очередь.** На одинаковом наборе вопросов сравните результаты при 1, 2 и 4 одновременных обращениях из разных чатов. Замерьте p95 от поступления вопроса до отправки ответа, долю таймаутов и ошибок. В метриках vLLM полезны `vllm:num_requests_waiting` и `vllm:request_queue_time_seconds`. При задержке без очереди измерьте отдельно эмбеддинги, поиск, реранкинг и агентные вызовы.
- **Граница наблюдаемости.** Кампусный Compose выключает Langfuse и файловый журнал диалогов. История диалога и лимиты хранятся в памяти бота и сбрасываются при перезапуске. Для постоянного мониторинга полезно добавить технические метрики приложения без текстов вопросов: длительность этапов, ошибки и частоту перехода на запасной режим.
- **Сравнение качества.** Используйте один и тот же набор вопросов и одного независимого судью для обоих режимов или оценивайте ответы вручную. Текущий `eval/run_answers.py` по умолчанию использует ту же модель как отвечающую и как судью. Опубликованные результаты внешнего API и результаты локального инференса следует сравнивать с учётом этой настройки.

## Что изменено в коде

- `rag/llm.py` принимает `LLM_BASE_URL`, `LLM_MODEL`, `LLM_BACKEND` и лимит ответа. Для vLLM отправляет настройки шаблона Qwen3 без режима рассуждений.
- `rag/embed.py` направляет запросы эмбеддингов в отдельный OpenAI-совместимый сервис. `rag/rerank.py` берёт имя модели из окружения. Для первого запуска используется та же Qwen3, что и для генерации.
- `rag/index.py` умеет пересчитать эмбеддинги уже собранных фрагментов. Для кампусного режима путь назначения отдельный.
- `compose.campus.yml` связывает сервисы CPU-VM. Базовый `docker-compose.yml` продолжает использовать прежние настройки.
