# Эксперименты: выбор компонентов RAG-ассистента

Отчёт по экспериментам, на основании которых выбрана конфигурация ассистента для абитуриентов РТУ МИРЭА. Метрики поиска: R@k (доля вопросов, у которых правильный фрагмент попал в первые k результатов) и MRR. Оценка ответов: по шкале 0–2 моделью-судьёй на расширенном наборе golden (178 вопросов).

## Итоговая конфигурация

| Компонент | Выбор | Раздел |
| --- | --- | --- |
| Источники данных | сайт приёмной комиссии priem.mirea.ru и раздел «Институты и факультеты» сайта mirea.ru (296 страниц и сводки по институтам) | Расширение базы: разделы институтов |
| Нарезка на фрагменты | простой алгоритм, максимум 1200 символов, минимум 250 | Чанкинг и поиск |
| Поиск | гибридный: смысловой (bge-m3) и BM25, взвешенная сумма, α = 0,6 | Чанкинг и поиск |
| Реранкер | Mistral Small: из 20 кандидатов выбирает 5, видит по 1000 символов каждого фрагмента | Оценка качества реранкера |
| Число источников для модели | 5 | Подбор количества источников |
| Режим ответа | агент с инструментами: поиск по текстам выполняется всегда, плюс таблица программ (отбор, подсчёт, карточка); при сбое обычный режим | Агент с инструментами |
| Модель для ответов | DeepSeek V4 Flash, рассуждения выключены | Сравнение моделей для ответов |
| Судья | DeepSeek V4 Flash | Оценка ответов модели |

Результат на расширенном наборе: на обычных вопросах бот отвечает верно в 91% случаев, на вопросах без ответа отказывает правильно в 100%, на подсчётах и фильтрах верно в 47%.

## Чанкинг и поиск

Проводилось сравнение алгоритмов для чанкинга (простой и сложный, с дублированием заголовков), также сравнивались способы расчета скора при поиске: смысловой, bm25, RRF, гибридный с взвешенной суммой. Подбирались гиперпараметры минимальной и максимальной длины чанков, а также параметр $\alpha$ для гибридного поиска.

Для сравнения результатов использовался golden датасет (на момент этих экспериментов около 60 вопросов, позже он вырос до 69, см. ниже): 40 обычных вопросов, 10 вопросов на подсчет, остальные не относящиеся к базе знаний. В качестве метрик используется $R@k$ и $MRR$.

| simple     | dense              |     0,47 |     0,78 |     0,85 |     0,60 |
| simple     | bm25               |     0,40 |     0,75 |     0,82 |     0,56 |
| simple     | rrf                |     0,62 |     0,88 |     0,90 |     0,72 |

| full       | bm25               |     0,38 |     0,65 |     0,80 |     0,52 |

Лучший результат показали простая нарезка с гибридным способом поиска (взвешенная сумма). Смысловой поиск ошибается на точных кодах программ, поэтому bm25 помогает ему в этом. В этом сравнении использовалось α = 0,7; итоговое значение 0,6 подобрано ниже.

## Оценка ответов модели

Скрипт получает ответ модели (поиск 20 кандидатов, реранкер Mistral Small выбирает 5, ответ DeepSeek V4 Flash, для уточняющих вопросов с историей), и проверяет его двумя способами:
- **без модели:** есть ли в ответе все строки из `must_contain` («слова», пробелы не важны) и ссылается ли ответ на нужную страницу («источник»);
- **модель-судья** (DeepSeek V4 Flash) сравнивает ответ с эталоном и ставит 2 (верно), 1 (частично), 0 (неверно). Для вопросов без ответа верно вежливый отказ без выдумок и без выполнения просьбы.

### Оценка судьи

Оценки судьи проверены вручную: прочитаны все 14 вопросов без ответа и 21 обычный вопрос с оценкой 0 или 1.
- **Отказы (14 из 14):** судья прав в каждом случае (погода, стихи, анекдот, пират, «игнорируй инструкции», другие вузы, несуществующий филиал, 2025 и 2027 годы, запись на программу).
- **Обычные вопросы:** примерно половина низких оценок справедлива (реальные ошибки бота), вторая половина занижена: судья снижал балл за лишнюю информацию о других уровнях образования, за детали из источников, которых нет в эталоне.
- **Правки промпта судьи:** (1) лишняя информация не снижает оценку, пока есть все факты эталона и нет противоречий; (2) оценивать только то, о чём спросили; (3) не придираться к году, если в эталоне его нет; (4) судье сообщается тип вопроса (ответ есть или нет): без этого он принимал отказ за правильное поведение там, где ответ существует; (5) сведения из источников, которых нет в эталоне, не считаются выдумкой.

**Качество от K не зависит в пределах шума**. 143 вопроса из 178 получают 2 при всех четырёх значениях, 14 не получают 2 ни при одном, и только 23 меняют оценку, причём без закономерности. Это обычный разброс ответов и реранкера, как и между повторными прогонами.

**Решение: оставить K = 5. Ни одно значение не даёт заметного выигрыша.**

## Расширение базы: разделы институтов

Первоначальная база собрана с сайта приёмной комиссии priem.mirea.ru. Чтобы бот отвечал и на вопросы про институты (руководство, кафедры, направления, контакты), добавлен раздел «Институты и факультеты» сайта mirea.ru. Новые данные сначала добавлялись в пробный индекс (`index/trial`: основной индекс плюс новые фрагменты, остальные не пересчитывались), и по результатам сравнения решено добавить их в основной.

### Сбор и обработка данных

Парсер запускается отдельно для нового источника и пишет в свою папку (`data_institutes`), поэтому основную базу заново собирать не пришлось. Получено 296 страниц (2 МБ) по 7 институтам: структура и кафедры, программы обучения, руководство, контакты, история, партнёры, инфраструктура. Всего 1149 фрагментов.

При сборе пришлось решить несколько проблем:

- сайт отвечал ошибкой 429 (слишком частые запросы), 118 страниц из 171 не скачались: уменьшили параллельность и увеличили паузы и число повторных попыток, парсер стал учитывать заголовок `Retry-After`;
- в каждой странице был блок настроек для слабовидящих (размер шрифта, кернинг и т. п.): строки вырезаются, как и повторяющийся хвост заголовка;
- библиотека для извлечения основного текста (trafilatura) на части страниц возвращала только меню, из-за чего разные страницы совпадали по тексту и пропадали как дубликаты: для этого источника берётся весь текст страницы;
- в полном тексте страницы остаётся меню на 2000 строк (средний размер страницы 118 КБ, всего 75 МБ): после обхода убираются блоки из трёх и более подряд идущих строк, которые повторяются на пяти и более страницах. Одиночные повторяющиеся строки («Заведующий кафедрой») остаются, иначе пропадали должности;
- страницы с достижениями студентов (около 390 однотипных страниц) исключены, на число страниц поставлен потолок.

Кроме страниц, по ним автоматически собраны 10 сводок (143 фрагмента): перечень институтов, направления подготовки с указанием институтов, кафедры и подразделения с заведующими и по одной сводке на каждый институт (руководство, направления со ссылками, кафедры, контакты учебного отдела). Сводки нужны потому, что список институтов на сайте лежит в меню, а перечни направлений и кафедр разбросаны по десяткам страниц. Размер индекса вырос с 4476 до 5768 фрагментов.

Для проверки в golden-набор добавлено 19 вопросов про институты (набор `inst`): 12 обычных (кто директор, кто заведует кафедрой, адреса и кабинеты, часы приёма), 5 перечней (направления института, список институтов, в каком институте есть направление) и 2 вопроса без ответа.

- Данные двух сайтов расходятся в том, к какому институту относится направление; бот может ответить по любому из источников.

## Агент с инструментами

Подсчёты и фильтры («сколько программ…», «какая самая дорогая», «у каких программ больше 35 мест») нельзя решить поиском по текстам: ответ складывается из десятков страниц. Для них сделан агент: модель сама выбирает инструмент, код выполняет его и возвращает результат. Инструменты работают с таблицей из 197 программ приёма (`index/programs.json`, собрана из страниц направлений: места, цены, проходные баллы по годам, предметы, срок, институт, описание программы):

- `find_programs`: отбор по условиям (уровень, институт, число мест, проходной балл, цена, предмет, срок и т. д.), сортировка, лимит;
- `count_programs`: подсчёт программ или направлений, с группировкой;
- `get_program`: карточка программы по названию или коду (числа и описание); при нескольких подходящих программах возвращает список для уточнения;
- `compare_programs`: сравнение двух-пяти программ, показатели и итог («у какой выше») считает код;
- `search_docs`: обычный поиск по текстам с реранкером.

Аргументы описаны моделями pydantic: схемы инструментов строятся из них, а аргументы, которые вернула модель, проверяются, и ошибка возвращается модели текстом, чтобы она исправила вызов. Таблица воспроизводит эталонные числа (56 магистерских программ на 2 года, 40 направлений магистратуры, 76 бакалаврских на 4 года, самая дорогая программа 709000 ₽).

Проверка проводилась на 117 вопросах (исходный набор v1, новые вопросы v2, вопросы про институты): все 22 агрегации, 79 обычных вопросов и 16 без ответа. Базой служит обычный режим на том же индексе. Было три прогона агента.

| Группа | Обычный режим | Агент v1 | Агент v2 | Агент v3 |
| --- | --- | --- | --- | --- |
| Обычные (79), верных | 96% (1,94) | 90% (1,85) | 97% (1,97) | 91% (1,89) |
| Агрегации (22), верных | 50% (1,09) | 73% (1,55) | 73% (1,55) | **82% (1,77)** |
| Без ответа (16), верных | 100% | 100% | 100% | 100% |
| Все (117), верных | 88% (1,79) | 88% (1,81) | 93% (1,90) | 91% (1,88) |
| Время на вопрос | 13,6 с | 14,7 с | 12,2 с | 14,9 с |

- **v1.** Агрегации заметно лучше, но на обычных вопросах 90% (v2: 71% на новых вопросах): агент часто отвечал без источников, по памяти, без вызова инструментов и без поиска. Кроме того, нашлись пробелы в самих инструментах: не было проходного на платное в карточке, нельзя было задать срок «5 лет 6 месяцев», подсчёт считал программы, а не направления.
- **v2.** Исправлены инструменты, и поиск по текстам теперь выполняется всегда, а инструменты его дополняют: агент не может ответить без источников. Обычные вопросы вернулись на уровень обычного режима (97%), ни одного вопроса хуже базы.
- **v3.** В сообщение добавлено напоминание, что на вопросах про количество, максимум или минимум и списки по условию источники неполные и нужно вызывать инструменты. До этого на четырёх агрегациях (g019, g023, g024, x25) агент их не вызывал и отвечал по фрагментам. Все эти четыре теперь верны: на агрегациях верных 18 из 22. Из первой попытки третьего прогона часть вопросов оборвалась из-за исчерпанного баланса у провайдера; после пополнения невыполненные вопросы дозапущены (`--resume`).

Итоговый прогон (v3), по вопросам: лучше базы у 13 вопросов (g019–g025, g048, x06, x25, i13, i14, i17), хуже у 7 (g017, g046, g065, x08, x09, x14, i15). Из ухудшений: g046 (сравнение скидок, неустойчиво во всех прогонах), x08 (в одном ответе модель ответила приветствием, не заметив вопрос), g065 («какие программы бакалавриата есть»: агент перечислил 81 программу бакалавриата вместо 97 программ бакалавриата и специалитета), остальные мелкие уточнения, за которые судья снижает оценку. Разброс между прогонами v2 и v3 на обычных вопросах (97% и 91%) показывает уровень шума, около 3–5 пунктов (три-четыре вопроса из 79).

Расход: в среднем 12,4 тысячи токенов на входе на вопрос против 8,0 тысяч в обычном режиме и 280 токенов на выходе против 150 (в каждый запрос добавляется описание инструментов, на вопросах с подсчётами модель обращается 2–4 раза). Основная часть токенов (около 5 тысяч на вопрос) приходится на реранкер, он такой же, как в обычном режиме. По оценке, на вопрос это около 2 копеек против 1,3.

**Решение: включить агента по умолчанию** (с запасным вариантом: при сбое инструментов бот отвечает обычным способом). Агрегации выросли с 50% до 82% (+32 пункта), обычные вопросы и вопросы без ответа остались на прежнем уровне в пределах шума, время не выросло, стоимость увеличилась на копейки.

Дополнительная проверка на новых для агента вопросах: 80 перефразировок обычных вопросов (набор para), на которых раньше агента не запускали. Агент ответил верно на 95% (1,93), обычный режим на том же индексе на 92% (1,89): лучше у 3 вопросов, хуже у 2, ошибок API и пустых ответов нет, ответов без ссылок (кроме отказов) нет. Инструменты вызваны в 19 вопросах из 80 (`search_docs` 10 раз, `get_program` 7, `find_programs` 5). Всего на 159 обычных вопросах (79 из основной проверки и 80 перефразировок) агент ответил верно на 148 (93%), обычный режим на 150 (94%): разница в один вопрос, то есть агент обычные вопросы не портит. Время на вопрос в этом прогоне выросло (22 с против 13,7 с у обычного режима), но прогоны выполнялись в разное время, поэтому разницу во времени нужно проверять отдельно на реальной работе бота.

## Векторная база Qdrant

Проверено, что даёт векторная база Qdrant по сравнению с текущим поиском на numpy (смысловые векторы и BM25 считаются в памяти, слияние взвешенной суммой). Готовые векторы и фрагменты загружены в локальное хранилище Qdrant без пересчёта эмбеддингов, BM25 добавлен как разреженные векторы (веса слов с учётом idf и длины документа). Сравнивались шесть вариантов на 175 вопросах (поиск без реранкера, R@1 / R@5 / R@20 / MRR; R@20 это полнота среди 20 кандидатов, которых получает реранкер):

- **numpy**: текущий поиск;
- **qdrant-weighted**: смысловой поиск в Qdrant, BM25 свой, то же слияние;
- **qdrant-rrf**, **qdrant-rrf60**, **qdrant-rrfw**: встроенное слияние Reciprocal Rank Fusion (по умолчанию, с константой 60, с константой 60 и весами 0,6 и 0,4 как у нашей суммы);
- **qdrant-dbsf**: встроенное слияние по распределению оценок.

| Вариант | Обычные (153) | Агрегации (22) | Время поиска, мс |
| --- | --- | --- | ---: |
| numpy | 0,56 / 0,88 / **0,99** / 0,69 | 0,18 / 0,55 / **0,77** / 0,33 | **7** |
| qdrant-weighted | 0,56 / 0,88 / **0,99** / 0,69 | 0,18 / 0,55 / **0,77** / 0,33 | 50 |
| qdrant-rrf | 0,54 / 0,82 / 0,97 / 0,66 | 0,27 / 0,50 / 0,64 / 0,39 | 98 |
| qdrant-rrf60 | 0,48 / 0,84 / 0,95 / 0,63 | 0,14 / 0,45 / 0,73 / 0,27 | 99 |
| qdrant-rrfw | 0,44 / 0,84 / 0,98 / 0,61 | 0,14 / 0,41 / 0,64 / 0,27 | 99 |
| qdrant-dbsf | 0,52 / 0,84 / 0,98 / 0,65 | 0,18 / 0,50 / 0,73 / 0,33 | 99 |

Выводы:
- **Перенос в Qdrant с нашим слиянием качество не меняет:** места правильного фрагмента совпали у numpy и `qdrant-weighted` для 175 из 175 вопросов.
- **Встроенное слияние Qdrant не лучше нашего.** По R@20 оно уступает на обычных вопросах 1–4 пункта (0,95–0,98 против 0,99), на агрегациях 4–13 пунктов (0,64–0,73 против 0,77), по R@1 и MRR тоже хуже. Даже RRF с нашими весами не помогает: RRF смотрит на места, а не на оценки, и теряет информацию о том, насколько фрагмент уверенно лучший. Поэтому свой BM25 и слияние взвешенной суммой (α = 0,6) остаются.
- **Скорость:** в локальном режиме Qdrant перебирает точки без сервера и в 7–14 раз медленнее numpy (50–99 мс против 7 мс), на фоне вызовов моделей по несколько секунд это не важно.
- Что Qdrant даёт по сути: фильтры по метаданным прямо в запросе (например, по уровню образования), добавление и замена документов без пересборки индекса, хранение вектора вместе с фрагментом (они не могут разойтись, в отличие от пары файлов `vectors.npy` и `chunks.json`), общий сервис для бота и API. Локальный режим допускает только один процесс, для бота и API нужен отдельный контейнер Qdrant.

Ход проверки: первый прогон встроенных режимов дал сильно заниженные результаты (R@5 на обычных вопросах 0,59–0,65) из-за ошибки в BM25-векторах: слова нумеровались в порядке обхода множества, который меняется от запуска к запуску, и номера при поиске не совпадали с записанными при сборке. После исправления (нумерация по алфавиту) BM25 в Qdrant совпал с `rank_bm25` (R@5 только по BM25 0,69 против 0,68, пересечение топ-10 8,3 из 10) и результаты стали такими, как в таблице.

## LlamaIndex

Поиск и ответ по фрагментам воспроизведены на LlamaIndex отдельно от основного проекта (папка `llamaindex_version/`, своё окружение), чтобы сравнить фреймворк с собственной реализацией. Данные и модели те же: готовые векторы bge-m3 из индекса `index/api` (5768 фрагментов), DeepSeek V4 Flash для ответа, Mistral Small для реранкера. Использованы готовые компоненты: `VectorStoreIndex` (смысловой поиск), `BM25Retriever`, `QueryFusionRetriever` (слияние `relative_score` с весами 0,6 и 0,4, как у нас), `LLMRerank`, `ResponseSynthesizer` с нашим системным промптом. Агент с инструментами, таблица программ, склейка фрагментов одного файла в источник и переписывание вопроса по истории в версию на LlamaIndex не переносились: у фреймворка нет готовых аналогов.

Метрики поиска без реранкера, 175 вопросов golden v3 (R@1 / R@5 / R@20 / MRR; R@20 это полнота среди 20 кандидатов, которых получает реранкер):

| LlamaIndex, BM25 по умолчанию, 100 кандидатов | 0,53 / 0,86 / 0,96 / 0,64 | 0,27 / 0,55 / 0,55 / 0,39 |
| LlamaIndex, BM25 по умолчанию, все фрагменты | 0,48 / 0,82 / 0,95 / 0,63 | 0,23 / 0,50 / 0,59 / 0,34 |

Реранкер Mistral Small (`LLMRerank`, 20 → 5) на кандидатах с BM25 по умолчанию: обычные 0,64 / 0,88 / 0,73 (R@1 / R@5 / MRR), агрегации 0,50 / 0,50 / 0,50. Реранкер на исправленном поиске (наш BM25, все фрагменты) не прогонялся.

Где возникает расхождение (смысловая часть и BM25 по отдельности, те же вопросы и фрагменты):

| Поиск | Обычные (153) | Агрегации (22) |

| BM25, наш (`rank_bm25`) | 0,29 / 0,68 / 0,86 / 0,45 | 0,05 / 0,18 / 0,36 / 0,11 |
| BM25, LlamaIndex по умолчанию | 0,27 / 0,64 / 0,83 / 0,43 | 0,09 / 0,14 / 0,50 / 0,14 |
| BM25, LlamaIndex с нашей токенизацией через `tokenizer` | 0,23 / 0,51 / 0,77 / 0,37 | 0,14 / 0,27 / 0,36 / 0,19 |

Выводы:
- **Смысловой поиск совпал полностью:** метрики одинаковые, первые десять результатов те же (10 из 10).
- **Расхождение даёт BM25.** Библиотека `bm25s` под `BM25Retriever` считает не так, как `rank_bm25`: пересечение первой десятки с нашей 6,1 из 10. Параметр `tokenizer` объявлен устаревшим и с нашей токенизацией работает хуже, чем без неё (R@5 0,51 против 0,64), поэтому вариант «с нашей токенизацией» не воспроизводит нашу токенизацию и честным сравнением считаться не может.
- **Глубина кандидатов важна на агрегациях.** LlamaIndex нормирует оценки только по кандидатам каждого поиска (по умолчанию в замере 100). На агрегациях R@20 при 100 кандидатах 0,59, при всех фрагментах 0,77.
- **Если подставить свой BM25 (собственный ретривер поверх `rank_bm25`) и брать все фрагменты, LlamaIndex повторяет наш поиск:** 0,56 / 0,88 / 0,99 на обычных и R@20 0,77 на агрегациях; разница по остальным показателям в один-два вопроса.
- **Из коробки LlamaIndex хуже на 3–5 пунктов на обычных вопросах и на 20 пунктов по R@20 на агрегациях.** Слияние и нормировка работают как задумано, потери создают готовые компоненты BM25 и значение глубины по умолчанию.
- **Время поиска не сравнивалось:** прогоны LlamaIndex считались вместе с запросами эмбеддингов или с полным слиянием по всем фрагментам; у numpy 7 мс без эмбеддинга.

**Решение: основной остаётся собственная реализация, LlamaIndex используется как отдельная версия для сравнения.** Качество не лучше, готовых аналогов агента, таблицы программ, склейки источников и переписывания вопроса нет, готовые компоненты приходилось проверять и подменять на данных проекта, а API фреймворка быстро меняется.

Ограничения: реранкер на LlamaIndex оценён только на кандидатах с BM25 по умолчанию; ответы модели через LlamaIndex (`llamaindex_version/ask.py`) судьёй не оценивались; один прогон на конфигурацию.
